Chain of Custody — every attempt, caught.

An AI agent that drafts performance-calibration packets for managers — wrapped in a security layer that checks not just who's asking for data, but who's about to read the answer. Five live attacks recorded end to end against the running app below. Not staged.

What's being caught

Caught Prompt injection — an embedded instruction tries to widen a manager's access to another team's data. Denied at the input gate before any data leaves the store.
Caught Wrong-reader leak — a manager's legitimate draft, addressed straight to the employee it's about, gets its private note and stack rank redacted before delivery. The rating still passes through; that's hers to see.
Caught Fabricated claim — a plausible-sounding line never backed by any real fetch gets blocked by a closed-world grounding check. Untraceable to a gated fetch means blocked by default.
Caught Tampered audit entry — a trace record edited directly on disk is caught twice, independently: the recomputed policy check disagrees, and the hash chain is broken.
Caught Forged token — a corrupted authentication token is rejected at login, signature verification failing before it ever reaches a scenario.

Why this exists

Nearly 90% of agent pilots never reach production — stalled in security review, not capability. Identity platforms scope what an agent can fetch. Almost none of them check what happens to that access afterward: an agent can be fully entitled to a fact and still leak it to the wrong reader. That failure mode is named directly in "Enterprise AI Must Enforce Participant-Aware Access Control" — Chain of Custody is a working answer to it, built and demoed end to end in one day.

Run it yourself

git clone https://github.com/bouncypitch/chain-of-custody.git && cd chain-of-custody && npm install && npm run dev — then open localhost:3000, log in as any org member, and run the four scenarios. Full details in the README.
